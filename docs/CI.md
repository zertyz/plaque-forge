# Continuous integration

Plaque Forge separates **validation** from **generated-artifact production**. Ordinary push/PR CI must answer whether the checked-in commit is acceptable; it should not silently change the commit it is evaluating.

## Change scope

`./scripts/analysis_change_scope.sh BASE HEAD` emits three conservative booleans:

- `needs_analysis`: Rust analysis, scenes, sources, or analysis workflow inputs changed.
- `needs_ml_analysis`: changes can alter ML-produced analysis artifacts.
- `needs_ml_runtime`: Python worker/setup/dependency code changed and the runtime itself must be rebuilt/verified.

This detector is an optimization only. It must prefer a false positive over missing a relevant gate.

## CI gates

The main workflow keeps the normal Rust/code and homologation gates and adds:

1. **analysis-no-ml-gate**: runs the six captured regression witnesses through `analyze_assets.sh --force --no-ml`. This protects the promised no-Python degradation path and reviewed static-layer compatibility.
2. **segmentation-runtime-gate**: on segmentation-tooling changes, installs/reuses a CPU-profile `/tmp/plaque-forge-python`, executes the complete setup smoke, and then repeats verification with Hugging Face and Transformers offline.

The CPU profile exists for hosted CI portability. It is a runtime/setup sentinel, not currently the canonical producer of committed ML analysis artifacts.

## Why CI does not auto-commit analysis

A workflow *can* commit generated files. With GitHub's repository `GITHUB_TOKEN`, the resulting ordinary push intentionally does not trigger another workflow run. That prevents recursion, but it also means the automation-created commit becomes a new branch HEAD without a new independent CI execution.

There is a second Plaque Forge-specific issue: committed ML analysis includes runtime provenance. A GitHub-hosted CPU runner is not automatically interchangeable with the local XPU runtime used for development. Choosing one as the canonical producer is a deliberate reproducibility policy, not a CI implementation detail.

Therefore normal validation CI remains read-only. If automatic analysis publication is added, use a separate trusted **producer** workflow with all of the following properties:

- an explicitly chosen canonical runner/runtime profile;
- narrow `contents: write` permission only on the producer job;
- no writes from untrusted fork pull requests;
- analysis + verification/homologation completed before publication;
- a bot branch/PR or explicit manual refresh preferred over mutating arbitrary contributor branches;
- provenance for the exact generated bytes;
- explicit recursion/concurrency guards if a GitHub App/PAT is ever used instead of `GITHUB_TOKEN`.

That separation keeps “the commit passed” and “automation produced a new commit” from being conflated.
